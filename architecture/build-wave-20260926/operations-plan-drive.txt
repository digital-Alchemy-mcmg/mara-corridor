5. TRAVELING ENVELOPE — SHARED I/O CONTRACT
==================================================


The traveling envelope is the common stage-boundary object for the entire build wave.


The envelope is not a side artifact. It is the I/O spine and the start/stop condition mechanism.


Scout initializes it.


Each downstream stage:
- receives the envelope
- validates its own start condition
- reads only the inputs it is authorized to read
- appends only its owned payload
- preserves earlier stage-owned material
- writes an append-log event
- advances stage state
- satisfies its stop condition
- hands the envelope forward


Conceptual structure:


traveling_envelope
  schema_version
  envelope_id
  created_at


  persistent
    target_identity
    application_routing
    source_identity


  stage_state
    current_stage
    completed_stages
    status


  append_log
    ordered stage events


  payload
    scout
    b
    b1
    b2
    b3
    b4
    b5


KEY RULE:


CARRIAGE != READ AUTHORITY.


A field may persist through the whole envelope because a later destination needs it. That does not mean every stage is allowed to reason over it.


Examples:
- application routing can travel end to end
- B1/B2 remain candidate-blind even if candidate information is physically carried elsewhere in the envelope
- B5 may receive the envelope but semantically reason only over B4-admitted/bounded candidate evidence


UPSTREAM IMMUTABILITY


No stage may silently rewrite a previous stage’s owned payload.


If a stage needs a corrected derivative, it creates a new stage-owned field or explicit repair record according to the architecture. It does not mutate history to make the pipeline look cleaner.

7. RUNNER TWO — B + B1 + B2 IMPLEMENTATION
==================================================


B — HANDOFF BOUNDARY


B validates the Scout envelope shape.


B does not:
- interpret candidate fit
- inspect candidate evidence
- perform target decomposition
- select Spatial DNA planes
- invent missing semantics


B checks:
- envelope version/shape
- required Scout payload
- required persistent target identity
- required routing/origin-destination structure
- correct incoming stage state


If the handoff is malformed:
- stop at B
- preserve the envelope
- record the failure
- do not fabricate the missing semantics


B1 — DECOUPLE


B1 is candidate-blind.


B1 answers:
WHAT DOES THIS TARGET OBJECT ACTUALLY CONTAIN?


B1 must preserve:
- target identification
- application routing
- exact source spans
- explicit requirements
- responsibilities
- qualifiers
- semantic force
- malform state where applicable


Semantic force must preserve the architecture:
- hard gate
- soft/contextual/interpretive
- unmarked role responsibility


A numeric requirement does not automatically become a hard gate merely because it contains a number.


B1 must not invent requirements from:
- job title
- occupational convention
- candidate background
- presumed business necessity


MALFORM RULE


Do not treat ordinary missing posting fields as automatic malform.


Missing salary, location detail, work arrangement, or requisition number does not automatically make a target malformed.


Use the established origin/destination logic.


B2 — CREATE TREE


B2 converts the B1 target decomposition into a deterministic addressable target tree.


Requirements:
- branches derive from the target itself
- no fixed occupational template
- deterministic lowercase alphanumeric hierarchical addresses
- bidirectional provenance between node and exact source span
- semantic class preserved
- meaningful relationships preserved
- many-to-many relationships allowed
- tree frozen before B3


ADDRESS RULE


Addresses are identifiers only.


They are not:
- scores
- weights
- confidence values
- ownership values
- magnitudes
- rankings


B1/B2 CANDIDATE QUARANTINE


Candidate evidence must not influence B1 or B2.


If an implementation shortcut allows candidate material to alter the target tree, that is a build defect.


B1/B2 STOP CONDITION


Runner Two reaches stage completion when:
- B accepts a valid Scout envelope
- B1 decomposition exists
- source spans/provenance are preserved
- semantic force is preserved
- B2 tree is built
- addresses are deterministic
- tree validates
- tree is frozen
- candidate data did not influence tree construction
- payload.b / payload.b1 / payload.b2 are appended appropriately
- stage state advances to B3
- runnable workbench demonstrates Scout-envelope → frozen-target-tree

8. RUNNER THREE — B3 IMPLEMENTATION
==================================================


B3 is the first stage that allows the frozen target tree to query candidate Spatial DNA evidence.


INVERSION RULE


The target node generates the question.


Candidate history does not generate the requirement.


For each target node:


1. form the satisfaction question
2. determine eligible Spatial DNA evidence planes from the target node/question
3. search candidate evidence
4. preserve atoms considered
5. select atoms actually submitted
6. produce bounded atomic blurbs if used
7. construct proposition
8. record rationale
9. append B3 binding record


DISCOVERY POSTURE


B3 may be permissive in discovery.


It may consider:
- direct evidence
- proximate evidence
- plausible evidence
- transferable evidence


But permissive discovery does not equal truth admission.


CONSIDERED VS SELECTED


This distinction must exist in the data model.


Do not bind every atom from an eligible plane merely because it was available.


B4 may later audit only what B3 actually selected.


PROOF PROHIBITIONS


B3 must not treat the following as proof:
- title alone
- occupational convention alone
- presumed necessity alone


B3 STOP CONDITION


B3 is complete when:
- every attempted target-node binding has an address reference
- satisfaction question exists
- eligible planes are recorded
- considered evidence is distinguishable from selected evidence
- selected evidence is traceable
- proposition exists where a proposition is submitted
- rationale exists
- B3 payload is appended
- stage state advances to B4
- workbench can run frozen-target-tree + candidate Spatial DNA → B3 submission payload

9. RUNNER FOUR — B4 IMPLEMENTATION
==================================================


B4 is the proposition-specific truth gate.


B4 owns:
- truth disposition
- scope
- admitted proposition
- evidence ceiling
- reason
- audit trace


B4 may consume only B3-selected evidence for the proposition being audited.


B4 must not search backward through the entire candidate corpus to rescue a proposition.


DISPOSITIONS


Use the locked truth states:


PASS / FULLY SUPPORTED


QUALIFIED / BOUND AT RESTRICTED SCOPE


UNRESOLVED AT ATOMIC LEVEL


CONTRADICTED


Every non-PASS disposition must preserve a reason.


HARD-GATE RULE


A hard gate cannot be converted into satisfaction by:
- narrowing the claim
- substituting adjacent experience
- calling a restricted scope equivalent
- relying on job title
- relying on convention
- relying on presumed necessity


If the required fact is not established, the gate is not satisfied.


EVIDENCE CEILING


B4 must emit the strongest allowed assertion boundary supported by the selected evidence.


Downstream stages may not silently expand beyond it.


B4 STOP CONDITION


B4 is complete when:
- every submitted B3 proposition has an auditable outcome
- only B3-selected evidence was used
- disposition is recorded
- admitted proposition is recorded where applicable
- bounded scope is recorded where applicable
- evidence ceiling is recorded
- reason is recorded for non-PASS
- hard-gate behavior is enforced
- ledger keys trace to B2 target addresses
- payload.b4 is appended
- stage state advances to B5
- workbench can run B3 submission → audited B4 ledger

13. RUNNER FIVE — ANTI-STALL WATCHDOG
==================================================


PURPOSE


Runner Five makes sure nobody “falls asleep on the clock.”


Runner Five owns no ordinary implementation stage at startup.


Its entire purpose is to keep blocked work returning to execution at the nearest available scheduling opportunity.


BLOCKER RECORD


When a build runner becomes blocked, it must persist:


- runner ID
- component/stage
- timestamp
- blocker code
- blocker description
- exact file/module/function where work stopped
- last valid commit SHA
- last valid traveling-envelope checkpoint if applicable
- command that failed
- relevant error
- condition required to clear blocker
- safe resume instruction


The blocked runner must then stop destructive work.


RUNNER FIVE WAKE LOOP


On every Runner Five wake:


1. inspect persisted blocker records
2. identify any active BLOCKED runner
3. determine whether the blocking condition still exists
4. do not perform broad architecture verification
5. do not redesign the blocked component merely to escape the blocker


IF NO BLOCKERS EXIST


Runner Five:
- records NO_ACTIVE_BLOCKERS
- sleeps until next scheduled wake


IF BLOCKER STILL EXISTS


Runner Five:
- leaves the stage checkpoint intact
- does not restart the stage
- does not erase the blocker
- reschedules itself at the nearest available scheduler slot
- sleeps


Do not default to waiting an hour if the scheduler offers an earlier slot.


IF BLOCKER IS CLEARED


Runner Five:
- resumes the blocked stage from the last valid checkpoint
- does not restart from zero unless the checkpoint is corrupted
- confirms work can proceed
- continues the blocked implementation
- establishes its next cadence relative to the time work resumed


IF A NEW BLOCKER OCCURS


Runner Five:
- persists the new blocker
- preserves the latest valid checkpoint
- schedules the nearest available retry
- sleeps again


IF THE ORIGINAL BUILD RUNNER IS AVAILABLE TO TAKE BACK OWNERSHIP


Runner Five may hand back the now-unblocked stage after preserving:
- the cleared blocker status
- current commit/checkpoint
- exact next action


The goal is continuity, not ownership competition.

26. WHAT COUNTS AS A TRUE BLOCKER
==================================================


Examples of true blockers:


- repository target cannot be identified
- required fixture corpus cannot be located
- required stage input contract is missing and no valid interpretation exists
- schema conflict prevents serialization/deserialization
- required dependency cannot be installed or accessed
- candidate Spatial DNA evidence source is unavailable for B3
- build cannot run because a required secret/service is unavailable
- upstream stage output is structurally incompatible with downstream start condition
- source documents contain a direct executable contradiction that cannot be resolved by precedence rules


Examples of things that are NOT automatically blockers:


- code could be prettier
- naming could be cleaner
- another architecture might be better
- more tests could theoretically be added
- documentation is not yet polished
- a non-critical refactor is desirable
- a future C-stage concern exists
- a future Weave concern exists
- a theoretical edge case outside current contract exists


Build the declared system.
